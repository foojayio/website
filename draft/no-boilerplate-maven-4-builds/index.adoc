Maven 4 GA is close. The final release is expected in 2026, or so they say. It is time to prepare.

This article covers what changes in your daily work with Maven 4, and how a base POM gives you builds with no warnings, no boilerplate and the same result every time.

== Maven 4 warns about plugin versions

Take the smallest possible project, with no parent and no plugin section, and build it with Maven 4:

----
[WARNING] Version not locked for default bindings plugins [maven-resources-plugin,
maven-compiler-plugin, maven-surefire-plugin, maven-jar-plugin], you should define
versions in pluginManagement section of your pom.xml or parent
----

Maven 3 builds the same project without a word.

The warning is fair. If you do not say which plugin versions to use, Maven picks its own defaults, and those defaults change from one Maven version to the next. The same source code can then build differently on two machines. The https://maven.apache.org/whatsnewinmaven4.html[Maven 4 notes] say: always define fixed versions of all the plugins you use.

To make the warning go away, you have to lock the version of every standard plugin. That is a block like this for each one, in every project you own:

[source,xml]
----
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-compiler-plugin</artifactId>
    <version>3.16.0</version>
</plugin>
----

Nobody wants to copy that into every project and keep the versions current by hand. The practical answer is a base POM: one parent that locks the versions for you.

== The fix: a base POM

Here is the same small project with the https://docs.flowlogix.com/base-pom[FlowLogix Base POM] as its parent:

[source,xml]
----
<parent>
    <groupId>com.flowlogix</groupId>
    <artifactId>base-pom</artifactId>
    <version>150</version>
</parent>
----

The build has no warnings. The project's own POM has no plugin section at all.

`base-pom` is deliberately small. It sets the Java release and the source encoding, and it locks the versions of the standard plugins: enforcer, compiler, surefire, failsafe, source, javadoc, dependency, deploy, release, clean, resources, jar, war, ear, install, jxr, site and project-info-reports. It adds no behavior. It is updated about once a week. To pick up a new release, you change one version number, and Dependabot or Renovate can do that for you.

=== Already have a company parent POM?

Keep it. Make the FlowLogix base POM the parent of your company's parent POM:

[source,xml]
----
<!-- your company's parent POM -->
<parent>
    <groupId>com.flowlogix</groupId>
    <artifactId>base-pom</artifactId>
    <version>150</version>
</parent>

<groupId>com.mycompany</groupId>
<artifactId>company-parent</artifactId>
<version>12</version>
<packaging>pom</packaging>
----

Your projects keep the parent they have today. Every one of them gets the locked plugin versions through it, and your company settings stay where they are. This is how you use the FlowLogix POM in corporate code without changing a single project.

== What about mixins?

A parent POM has one known limit. A project can have only one parent.

Maven's answer is https://maven.apache.org/guides/mini/guide-mixins.html[mixins], which let a project pull in shared build configuration from several places. According to the Maven guide, mixins come with Maven 4.2.0 and a new model version. My guess is that they will not be usable in everyday projects before 2028.

When mixins are available, FlowLogix will move from a base POM to mixins. Until then, a parent is the only way to get a warning-free build without copying plugin versions around.

== Use properties, not plugin configuration

Here is the second source of build boilerplate. To change one setting of one plugin, you normally write this:

[source,xml]
----
<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-surefire-plugin</artifactId>
            <configuration>
                <redirectTestOutputToFile>false</redirectTestOutputToFile>
            </configuration>
        </plugin>
    </plugins>
</build>
----

With a parent that exposes its settings as properties, such as the FlowLogix `infra-pom` described below, the same change is one line:

[source,xml]
----
<properties>
    <test.redirect.to.file>false</test.redirect.to.file>
</properties>
----

A property is also easy to change for one run, with no edit to the POM:

----
mvn verify -Dtest.redirect.to.file=false
----

This is the rule the FlowLogix POMs follow. Wherever a setting can be a property, it is one.

== No more `install` for multi-module projects

In Maven 3, working inside one module of a multi-module project was painful. Either you ran `mvn install` first, which copies half-finished artifacts into your local repository, or you stayed at the top and typed flags such as `-pl :app -am` every time.

Maven 4 removes both. I tested this with a project that has two modules, where `app` depends on `lib`.

[cols="3,1,1", options="header"]
|===
| Step | Maven 3 | Maven 4

| `mvn verify` at the top of the project
| Passes
| Passes

| Then `cd app` and `mvn test`
| Fails, `lib` cannot be found
| Passes
|===

Maven 4 keeps the modules it has built in a repository inside the project itself. Nothing is written to `~/.m2`. Build the project once with `mvn verify`, and from then on you can run tests from inside any module.

The Maven team's own advice is the same: do not use `mvn clean install` for your regular builds. Use `mvn verify`.

Maven 4 also has `mvn -r`, which resumes a failed build from the module that failed, with no module name to type.

== Faster multi-module builds

Multi-module builds can run their modules in parallel. Add a build cache, and work that is already done is not repeated.

We measured a sample run with eight modules, each with one slow test. These are the results, and your mileage may vary:

* Building modules in parallel with `mvn -T 8` was 4 times faster than building them one after another.
* https://maven.apache.org/mvnd.html[mvnd], the Maven daemon, was 6 times faster. It builds modules in parallel by default and keeps a warm JVM between builds.
* With the https://maven.apache.org/extensions/maven-build-cache-extension/[Maven build cache], a repeated `mvn clean verify` was 6 times faster. With mvnd and the cache together, it finished in half a second.

The cache is one small file in your project, `.mvn/extensions.xml`. The starter project from https://start.flowlogix.com[start.flowlogix.com] comes with it already set up.

== No Maven to install or manage

You do not have to install Maven at all. The https://maven.apache.org/tools/wrapper/[Maven Wrapper] is a small `mvnw` script in your project that downloads the right Maven version the first time you run it. Everyone on the team, and your CI, builds with the same version.

Three things make it easy to live with:

* *One file of configuration.* The Maven version is one line in `.mvn/wrapper/maven-wrapper.properties`. There is no JAR file to commit.
* *Dependabot keeps it current.* Dependabot now updates the Maven Wrapper automatically, the same way it updates your dependencies.
* *A JDK on demand may come next.* There is an https://github.com/apache/maven-wrapper/issues/337[open proposal] for the wrapper to download the JDK as well, using the foojay Disco API. If it is accepted, a fresh machine will need nothing installed to build your project.

== What the Infra POM gives you

`base-pom` only locks versions. `infra-pom` is the next step up. It is the parent to use when you want a complete build with nothing to configure.

[source,xml]
----
<parent>
    <groupId>com.flowlogix</groupId>
    <artifactId>infra-pom</artifactId>
    <version>150</version>
</parent>
----

It is opinionated, and the opinions are not all or nothing. Every one of them is a property, so if you do not want it, you turn that one off in one line and keep the rest. Anything that costs time or needs outside setup is off until you ask for it.

Here is what you get:

* *Reproducible builds.* Every archive gets the same fixed timestamp. I built a project twice from clean, and the JAR, the sources JAR and the javadoc JAR had identical checksums both times.
* *Build checks.* The build stops early if Maven or the JDK is too old, if dependency versions disagree with each other, or if JUnit 4 sneaks in.
* *Useful compiler settings.* Warnings are shown, deprecated and unchecked code is reported, and parameter names are kept for Jakarta EE and other libraries.
* *Fast, useful tests.* Unit tests run in parallel and in random order, so tests that depend on each other show up early. Output goes to files, and the console stays quiet.
* *Integration tests wired in.* Any class named `*IT` runs in the integration test phase, and the build stops if one of them fails.
* *A demo directory facilitates clean documentation and compiled javadoc snippets.* See below.
* *Code style checks.* Checkstyle runs at the start of the build. See below for how to use your own license header.
* *API compatibility checks.* The build can compare your public API with the last release and fail on a breaking change. This is off until you turn it on.
* *Code coverage.* JaCoCo combines unit and integration tests across modules, including on application servers. It does nothing until you add the JaCoCo plugin to your project and run with `-Pcoverage`.
* *Versions of common libraries.* The Jakarta EE API, Lombok, Mockito and ShrinkWrap have versions set. Nothing is added to your project. A version applies only if you declare the dependency yourself.
* *Releases.* Artifacts are signed, uploaded together at the end, and published with a software bill of materials. None of it runs during a normal build.

The https://docs.flowlogix.com/base-pom[Base POM documentation] lists every property and how to change it.

NOTE: `infra-pom` loads Mockito as a Java agent for tests, the way current JDKs require, so your project needs Mockito as a test dependency. The `unit-test` https://docs.flowlogix.com/depchains[dependency chain] brings Mockito, JUnit and AssertJ in one dependency. If you do not use Mockito, set the `mockito.agentOptions` property to empty.

=== A demo directory

`infra-pom` adds one source folder that Maven does not have: `src/demo/java`.

Code in it is compiled and can be tested like test code, and it is not shipped in your JAR. It is the place for examples that show how your library is used. Because they are compiled on every build, they cannot go stale.

=== Javadoc with real snippets

Those demos can appear in your documentation. Mark a region in a demo class:

[source,java]
----
class GreeterDemo {
    String demo() {
        // @start region="greet"
        var greeter = new Greeter();
        return greeter.greet("Duke");
        // @end
    }
}
----

Then point to it from the javadoc of the class it documents:

[source,java]
----
/// Greets people.
///
/// {@snippet class="com.example.GreeterDemo" region="greet"}
public class Greeter {
----

The generated documentation shows the two lines of code from the demo. The example in your javadoc is code that compiled and passed a test.

Javadoc is kept in a separate profile, so it does not slow down your regular development builds. Run `mvn verify -Pdocs` when you want the documentation built.

=== Your own license header

Checkstyle is the most opinionated part of the POM. The default header is the Flow Logix one, so the first thing to do is to use your own. Put your header text in a file in your project, for example `src/checkstyle/header.txt`, and point one property at it:

[source,xml]
----
<properties>
    <checkstyle.headerLocation>${maven.multiModuleProjectDirectory}/src/checkstyle/header.txt</checkstyle.headerLocation>
</properties>
----

Every source file is then checked against your header. The starter project from https://start.flowlogix.com[start.flowlogix.com] is set up this way.

== What this buys you

Add the four pieces together:

* A base POM locks plugin versions, so Maven 4 builds with no warnings.
* Settings are properties, so your POM stays boilerplate-free.
* Maven 4 lets you build and test from inside any module, with no `install`.
* Parallel builds, mvnd and the build cache keep it fast.

The POM of a project built this way contains its name, its parent and its dependencies. That is all.
